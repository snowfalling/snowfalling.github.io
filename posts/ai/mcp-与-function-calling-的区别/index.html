MCP 与 Function Calling 的区别

很多人第一次接触 MCP（Model Context Protocol）时，都会本能地问出同一句：「它和 Function Calling 到底有什么区别？是不是二选一的替代方案？」

这个问题的答案是反直觉的——它们根本不处在可以"二选一"的同一个层次上。Function Calling 是模型自身暴露出来的一项基础能力；MCP 则是一个用来规范化"把工具、资源、提示词接入并分发出去"的客户端-服务器协议。更进一步说，MCP 里的「工具」最终往往还是要借助 Function Calling 才能真正落到模型手里去执行。

所以正确的问题不是"选哪个"，而是"它们分别解决什么问题，又如何串在一起"。下面先给结论，再展开。

一、一句话定位 #

维度Function CallingMCP
本质模型/API 的内建能力客户端-服务器协议
解决的问题让模型"学会调用外部工具"让工具"标准化地被接入和分发"
层次模型能力层工具接入/基础设施层
存在形态一种请求-响应的交互模式一套协议规范 + 一批实现
谁在用它直接调 API 的开发者想要"一次接入、多处复用"的场景

用一句话概括：

Function Calling 解决的是"模型能不能/怎么调用工具"；MCP 解决的是"工具从哪儿来、怎么统一接进来"。

二、什么是 Function Calling #

Function Calling 是大模型提供的一项能力：你在一轮对话里，把一组可调用的函数（工具）定义随请求一并告诉模型，当模型判断"这句话需要调用某个工具才能回答"时，它不会直接编答案，而是输出一段结构化的调用意图——包含要调哪个函数、传什么参数（JSON）。

流程通常是四步：

  1. 定义工具：你用 JSON Schema 描述每个工具的名字、用途、参数。
  2. 模型决策：模型判断是否要调工具，若要，则输出结构化的 tool_call（函数名 + 参数）。
  3. 你执行：应用侧真正去跑这个函数，拿到真实结果（比如查数据库、调天气 API）。
  4. 回填模型：把执行结果作为工具消息回传，让模型基于真实结果继续生成最终回答。

关键点在于：Function Calling 只负责"让模型表达出调用意图"，它本身并不执行任何函数。真正干活、返回结果的是调用方你的代码。模型拿到的是结果，而不是自己去跑。

三、什么是 MCP #

MCP 是一套开放协议，定义了客户端（Host）与服务器（Server）之间如何交换能力。它把"模型能用的外部能力"抽象成三类标准原语：

  • Tools（工具）：模型可以调用的动作，类似上面的函数。
  • Resources（资源）：可以被读入上下文的只读数据（文件、文档等）。
  • Prompts（提示词）：可复用的提示词模板。

它的价值在于标准化。在没有 MCP 之前，你想给模型接一个 GitHub、一个数据库、一个文件系统，往往要为每个来源各写一套对接代码、各定义一次 schema、各处理一遍鉴权和生命周期。MCP 把这些统一成一种协议：你只需要实现一个 MCP Server，任何支持 MCP 的客户端（Claude、Claude Code、各家 Agent 框架等）都能用同一个 Server 把能力接进去。

一句话：MCP 是"工具的资源池与分发标准"，解决了接入成本和互操作性问题。

四、核心区别：不在一个层次 #

把两者直接对比，就像拿"发动机"和"高速公路"比——它们都跟车有关，但解决的根本不是一件事。

维度Function CallingMCP
关注点模型这一侧如何表达调用工具这一侧如何接入
协议形态一种请求/响应的交互格式一套客户端-服务器协议
是否自身执行否，由应用侧执行否，由 MCP Server 执行
标准化对象工具调用的消息格式工具的接入与分发
依赖模型依赖模型支持该能力与模型解耦，是通用基础设施
单次性/复用性偏单次调用一次接入、多处复用

最容易被误解的一点是：MCP 并不是 Function Calling 的"替代品"。一个 MCP Server 暴露出来的 Tools，最终要真正被某个模型调用时，往往还是以 Function Calling 的形式进入模型的上下文、由模型输出 tool_call 再回填结果。也就是说：

MCP 在"接入层"做了标准化，Function Calling 在"模型层"做了标准化；前者把工具送到模型面前，后者让模型学会用。

五、它们怎么串起来 #

一个典型的协同链路如下：

[ 你的应用 / Agent Host ]
        │  (1) 通过 MCP 协议连接并发现能力
        ▼
[ MCP Server ]
        │  (2) 暴露统一的 Tools / Resources / Prompts
        ▼
[ Function Calling ]
        │  (3) 模型接收工具定义 → 输出 tool_call
        ▼
[ 应用执行 / MCP Server 执行 ]
        │  (4) 返回真实结果
        ▼
[ 模型基于结果生成最终回答 ]

可以看到，MCP 负责第 (1)(2) 步——把散落的外部能力标准化地接进来；Function Calling 负责第 (3)(4) 步——让模型真正调用这些能力。两者是串联、配合，而不是竞争。

六、什么场景选什么 #

既然不是二选一，真正该问的是：在这个项目里，我更需要解决接入问题，还是调用问题？

  • 只做一次性、单一工具接入（比如就接一个自研的内部 API）：直接用 Function Calling 定义 schema 即可，引入 MCP 反而增加一层抽象。
  • 需要把同一批工具给多个客户端/多个 Agent 复用：用 MCP 封装成 Server，接入成本从"N 套"降为"1 套"。
  • 围绕一个模型做深度的多工具编排：Function Calling 是绕不开的基础，MCP 可以帮你把工具来源管起来。
  • 要对接现成生态（GitHub、数据库、文件系统等）：优先找现成的 MCP Server，避免自己手写对接。

七、结论 #

  1. 它们不是替代关系，是不同层次的事物：Function Calling 是模型能力，MCP 是接入协议。
  2. Function Calling 解决"模型如何调用"，模型输出结构化调用意图，由应用/服务侧真正执行后回填。
  3. MCP 解决"工具如何接入"，把工具、资源、提示词标准化成可与模型解耦、可复用的基础设施。
  4. 实际工程里它们是配合关系：MCP 把工具接进来，Function Calling 让模型用起来。
  5. 选型时不要问"MCP 还是 Function Calling"，而要问：我是要解决接入/复用问题（倾向 MCP），还是要解决单点调用问题（直接用 Function Calling 就够）。
