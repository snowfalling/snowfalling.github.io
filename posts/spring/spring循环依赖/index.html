什么是循环依赖 #

循环依赖指两个或多个 Bean 相互引用，形成闭环。比如 A 依赖 B，B 又依赖 A：

@Component
class A { @Autowired B b; }

@Component
class B { @Autowired A a; }

如果没有特殊处理，创建 A 时要先创建 B，创建 B 时又要先创建 A，就会陷入死循环。

核心机制：三级缓存 #

Spring 解决循环依赖的核心是三级缓存，都定义在 DefaultSingletonBeanRegistry 中。

一级缓存 singletonObjects，存放完全初始化好的成品 Bean，可直接对外使用。

二级缓存 earlySingletonObjects，存放提前暴露的、尚未完成属性填充和初始化的"半成品"Bean（早期引用）。

三级缓存 singletonFactories，存放 Bean 的工厂对象 ObjectFactory。调用它的 getObject() 能拿到早期引用，如果需要 AOP 代理，代理对象也在这里生成。

// DefaultSingletonBeanRegistry 中的三级缓存
private final Map<String, Object> singletonObjects = new ConcurrentHashMap<>(256);
private final Map<String, Object> earlySingletonObjects = new ConcurrentHashMap<>(16);
private final Map<String, ObjectFactory<?>> singletonFactories = new HashMap<>(16);

解决流程（以 A、B 互相依赖为例） #

创建 A 时，先实例化（调用构造器 new A()），得到一个原始对象。此时立刻把一个能返回 A 早期引用的 ObjectFactory 放入三级缓存。

接着给 A 填充属性，发现它依赖 B，于是转去创建 B。

创建 B 时同样先实例化，放入三级缓存。给 B 填充属性时发现它依赖 A，于是去缓存里找 A。一级缓存没有、二级缓存没有，但三级缓存里有 A 的工厂。调用工厂的 getObject() 拿到 A 的早期引用（如需 AOP 则此时生成代理），把它从三级缓存移到二级缓存，然后注入给 B。

B 拿到 A 的引用后就完成了属性填充和初始化，成为成品，放入一级缓存。

回到 A 的创建流程，A 现在能拿到成品 B 完成注入，A 也初始化完成，放入一级缓存。循环解开。

获取单例时的三级查找逻辑如下：

protected Object getSingleton(String beanName, boolean allowEarlyReference) {
    Object singletonObject = this.singletonObjects.get(beanName);        // 一级
    if (singletonObject == null && isSingletonCurrentlyInCreation(beanName)) {
        singletonObject = this.earlySingletonObjects.get(beanName);      // 二级
        if (singletonObject == null && allowEarlyReference) {
            ObjectFactory<?> factory = this.singletonFactories.get(beanName); // 三级
            if (factory != null) {
                singletonObject = factory.getObject();  // 触发早期引用/代理生成
                this.earlySingletonObjects.put(beanName, singletonObject); // 升级到二级
                this.singletonFactories.remove(beanName);
            }
        }
    }
    return singletonObject;
}

为什么需要三级而不是两级 #

这是理解三级缓存的关键。核心答案是：三级缓存的存在不是为了"解决循环依赖"，而是为了在解决循环依赖的同时，兼顾 AOP 代理的正确时机。

没有 AOP 的情况：两级确实够用 #

如果 Bean 不需要代理，那对外暴露的就是原始对象本身。创建 A → 实例化后把 A 的半成品放进二级缓存 → 填充属性发现依赖 B → 创建 B → B 从二级缓存拿到 A 的半成品注入 → B 完成 → A 完成。整个过程 A 始终是同一个对象，二级缓存足矣。所以单纯解决循环依赖，两级足够。

引入 AOP 后，注入的必须是代理对象 #

关键前提：如果 A 被 AOP 增强（比如加了 @Transactional），那么最终容器里、以及注入给别人的，都必须是 A 的代理对象，而不是原始的 A。否则 B 拿到的是没有事务功能的原始 A，就出 bug 了。

而正常情况下，代理对象是在 Bean 初始化的最后一步（BeanPostProcessor 的 after 阶段）才生成的。也就是说，A 刚实例化时还是原始对象，代理还没产生。矛盾就此产生：循环依赖时，B 要在 A 还没走完初始化、代理还没生成时就拿到 A 的引用，它拿到的到底该是什么？

假设只用两级缓存，会怎样 #

方案一：二级缓存里存原始对象。 那 B 注入的是原始 A。但 A 后续会生成代理，最终进一级缓存的是代理 A。结果 B 手里是原始 A，容器里是代理 A，两个不是同一个对象，事务失效。错误。

方案二：实例化后就立刻生成代理，放进二级缓存。 这样 B 拿到的就是代理 A，一致了。但代价是只要用了这套机制，所有 Bean 都得在实例化后马上提前生成代理，即使它根本没有循环依赖。这违背了 Spring “代理应在初始化最后统一生成"的设计，把代理时机强行提前，破坏了正常生命周期。

三级缓存的巧妙之处：用工厂"按需、延迟"决定 #

三级缓存存的不是对象，而是一个工厂 ObjectFactory：

addSingletonFactory(beanName, () -> getEarlyBeanReference(beanName, mbd, bean));

这个工厂平时不执行。只有真正发生循环依赖、别人来提前索要引用时，才会调用 getObject()，此时才判断"这个 Bean 需不需要代理”，需要就当场生成代理并返回，然后升级到二级缓存。

这带来两个好处：没有循环依赖时，工厂永远不会被调用，A 走完正常流程、在初始化末尾正常生成代理，代理时机没有被打乱；有循环依赖时，工厂被触发，提前把代理生成出来给 B，并存入二级缓存，保证 A 后续要用时拿到的、以及最终进一级缓存的，都是同一个代理对象。

一句话总结：三级缓存里的工厂，本质是一个"延迟且按需的代理生成开关"。两级缓存要么保证不了一致性（存原始对象），要么就得牺牲代理时机、无差别地给所有 Bean 提前建代理（存代理对象）。而三级缓存用一个工厂把"是否要代理、什么时候代理"这个决定推迟到真正需要的那一刻，既解决了循环依赖，又不打扰没有循环依赖的正常 Bean。所以三级不是为循环依赖多出来的，而是为 AOP 与循环依赖共存而设计的。

Spring 无法解决的循环依赖 #

构造器注入的循环依赖无法解决。 因为提前暴露早期引用的前提是对象已经被实例化（new 出来了），而构造器注入要求在构造时就拿到依赖，此时对象还没实例化完成，无法放入三级缓存。这种情况 Spring 会抛出 BeanCurrentlyInCreationException。

@Async 注解的 Bean 循环依赖也可能失败。 因为 @Async 的代理是在初始化后期（BeanPostProcessor 的 after 阶段）才生成的，而循环依赖时提前暴露的是尚未被 @Async 代理的对象，导致最终注入的引用与一级缓存里的代理对象不一致，Spring 检测到后会报错。

原型（prototype）作用域的循环依赖无法解决。 因为原型 Bean 每次获取都创建新实例，Spring 根本不会缓存它们，无从提前暴露引用。

应对与规避建议 #

优先使用 setter 注入或字段注入（而非构造器注入）可以让 Spring 自动解决循环依赖。但更好的做法是从设计上避免循环依赖——它往往是职责划分不清的信号。如果必须保留，也可以用 @Lazy 注解延迟其中一个依赖的加载来打破闭环，或者把公共逻辑抽取到第三个类中重构掉循环。
